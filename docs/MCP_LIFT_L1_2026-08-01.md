# MCP lift - L1 result (2026-08-01)

L1 was the free/local phase of `mcp-lift-phases` (BACKLOG.md): a one-shot
`skylos` scan over `tools/` + `ops/`, and verification of the two CLI flags L2
rests on. Both ran. Both changed the plan.

## 1. L2's headline flag DOES NOT EXIST on the installed CLI - L2 is dead

`--append-subagent-system-prompt` was filed as "the highest-value item found and
it was NOT on the operator's list". Measured on this machine:

```
claude --version   -> 2.1.220 (Claude Code)
claude --help | grep -i subagent   -> --forward-subagent-text   (ONLY match)
```

The only append flags that exist are `--append-system-prompt` and
`--append-system-prompt-file`. Neither is subagent-scoped.

This is the SECOND leg to fail under L2. The first was its premise: L2 was
justified because PreToolUse hooks were believed not to reach headless
`claude -p --permission-mode bypassPermissions`. That belief was measured false
on 2.1.220 and corrected in CLAUDE.md (`e436128`); RM independently confirmed
its own gate fires headless AND covers `--no-verify`, which the git hook cannot
see.

**Ruling: L2's `--append-subagent-system-prompt` half is CLOSED - not deferred.
A flag that does not exist cannot be adopted, and the problem it was going to
solve does not exist either.** The `red-handed` half of L2 is untouched by this
and stays open on its own merits.

## 2. skylos ran, but neither "no install" nor its precision survived contact

- `skylos@latest` (4.32.0) is NOT installable here: it depends on
  `tree-sitter-dart-orchard`, which has no Windows wheel and needs MSVC 14+
  build tools. The "no install, no key" framing held only for the key.
  Working invocation, wheels-only: `uvx skylos==3.0.0 <dir>` (2.4.0 also works;
  1.9.0 and `--python 3.12` both fail).
- It takes ONE directory per run: `uvx skylos==3.0.0 tools ops` silently treats
  `ops` as a deployment subcommand and fails. Scan each dir separately.

Yield: 34 items in `tools/`, 8 in `ops/`. Spot-checking the highest-confidence
findings, the majority are false positives, several dangerously so:

| flagged | verdict | why |
|---|---|---|
| `lw_httpd.py:122 allow_reuse_address` | **FP - load-bearing** | `False` IS the single-instance guard; a hard bind failure is the mechanism. Deleting it lets a second server steal the port. |
| `lw_httpd.py:119/133 daemon_threads`, `protocol_version` | FP | framework class-attr overrides, read by socketserver not by us |
| `GpuBusy` imports (`lw_clean_pass:65`, `lw_gen_qa:53`) | FP | deliberate re-export, already `# noqa: F401` |
| `lw_upscale.py:466 first_pass` | FP | 55 references |
| `lw_rundash_state.py:547 read_cycle_history` | **skylos was RIGHT, this row was wrong** | first called it an FP on a raw count of 12 references. Those 12 were its own definition plus tests: it had NO production consumer at all. Not dead code (tests covered it), but a reader nothing called. Wired into `/api/run` the same day - see LEDGER 65. |
| `dwpose_onnx/*` | out of scope | vendored third-party |
| `lw_ports.py:42 in_block`, `lw_g1_gate.py:695 verdict` | plausible | 1 reference each (its own def) |

**Ruling: do NOT wire skylos into CI or drift_guard.** On this repo it flags a
guard whose whole purpose is to look inert. It is usable as a one-shot
human-read hint, at the pinned version above, and nothing more.

**Correction, same day.** The triage above dismissed `read_cycle_history` as an
FP on a raw reference count. That was wrong, and the way it was wrong is worth
keeping: counting references without reading them cannot tell a live consumer
from a test. Every one of its 12 references was its own definition or a test -
skylos had found a real hole. Grepping a count is not verification; the rule in
CLAUDE.md is to re-probe the source of truth, and a count is not that.

## 3. What the scan actually earned: five forked `GpuBusy` classes

The one finding worth keeping is one skylos did not make - it fell out of
chasing an "unused import". `gpu_lock` + `GpuBusy` are FORKED, not shared:

```
class GpuBusy(RuntimeError)   lw_g1_gate.py:61   lw_upscale.py:64
                              lw_gen_run.py:69   lw_clean_sdxl.py:70
def gpu_lock(...)             the same four, plus re-exports
```

`lw_g1_gate.py:48` even documents the fork ("rather than forking a fifth").
`except GpuBusy` binds to ONE of those classes, so a catch site only covers a
raise from its own module's lock. Today the pairings happen to line up, but
nothing enforces it and every new GPU consumer is a coin flip.

Two live consequences, both un-covered:

- `lw_clean_iopaint.py:553` enters `C.gpu_lock(dev)` and never mentions
  `GpuBusy`. A mutex timeout there exits with a raw traceback - against the
  CLAUDE.md "Error Handling" rule (friendly degraded-mode message, raw error to
  `logs/`). This is the Stage-2 cleaning path that just ran 12 slugs.
- `lw_gen_weaponpass.py:251,301` enters `gr.gpu_lock` with no `GpuBusy` handler;
  it survives only via the broad `except Exception` at :850.

This matters more now than when the fork was written: N=3 concurrent repos means
GPU contention is the expected case, not the edge case. Filed as its own item.
