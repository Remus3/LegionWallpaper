# P3 - MediaWiki canonical-source probe - RESULT (2026-08-01)

Phase P3 of `mcp-lift-phases` (BACKLOG), operator-gated, gate lifted 2026-08-01.
Predecessors: `MCP_LIFT_TRIAGE_2026-08-01.md` (scores), `MCP_LIFT_DIVE_2026-08-01.md`
(the 63-entry dive that replaced L3/L4 with P1-P5). P1 shipped as LEDGER 71, P2 as
commit `9d63303`.

## The question P3 was gated on

The dive framed it as one falsifiable probe: **does `professionalwiki/mediawiki-mcp-server`
return image BYTES from a Fandom wiki?** If no, fall back to `olgasafonova`.

## The answer

**YES on the capability, NO on the server.** A MediaWiki wiki serves LW canonical
splash art anonymously, at resolutions far above the 2560x1440 target. But the
probe was run against the Action API directly - which is what BOTH candidate MCP
servers wrap - and the API answers in ~40 lines of stdlib `urllib`, the same
transport `tools/lw_recover.py` already uses. Neither server is warranted:
adopting one buys a Node (professionalwiki) or Go/Docker (olgasafonova)
dependency for zero capability LW does not already have.

The impl choice INVERTED once in the dive (professionalwiki over olgasafonova, on
`get-file-data`). It inverts a second time here: **neither**. The row is not
closed as a dead end - the SOURCE is adopted, the WRAPPER is declined.

## What was measured

Three probe rounds, network-live, read-only, all against real corpus champions.
Scripts kept in the session scratchpad (throwaway - the reusable form is the
tier itself, if that is ever funded).

### Round 1 - both wikis answer anonymously

| | leagueoflegends.fandom.com | wiki.leagueoflegends.com (wiki.gg) |
|---|---|---|
| `meta=siteinfo` | 200, MediaWiki 1.43.9 | 200, MediaWiki 1.45.3 |
| `list=allimages` anonymous | yes | yes |
| `Vayne_OriginalSkin_HD.jpg` | 7200x4400 declared | 7200x4400 declared |
| bytes returned | 200 | 200 |

No account, no key, no token on either. This is a network dependency, not a
metered one, exactly as the dive predicted.

### Round 1 caught a trap: Fandom silently transcodes to WEBP

The API declares `Vayne_OriginalSkin_HD.jpg` as **8,799,303 B image/jpeg**. The
URL the API itself returns hands back **2,473,238 B of WEBP** - 28 percent of the
declared size, a lossy re-encode, under a `.jpg` name and with no `Content-Type`
header to give it away. Pixel dimensions are preserved (7200x4400), so a
dimensions-only check reads clean. This is precisely the class of defect
`first-pass-alpha-letterbox` is: an unannounced format conversion that every
cheap check passes.

### Round 2A - byte fidelity, all fetch paths

Both wikis declare the SAME upstream sha1 (`84d1c438...`), so both host the same
canonical upload. **No fetch path returns bytes matching that sha1:**

| path | bytes | format | sha1 matches declared |
|---|---|---|---|
| declared (both APIs) | 8,799,303 | JPEG | - (the reference) |
| fandom, URL as returned | 2,473,238 | **WEBP** | no |
| fandom, `/revision/` stripped | 2,473,238 | **WEBP** | no |
| fandom `?format=original` | 8,792,719 | JPEG | no |
| fandom `/revision/latest&format=original` | 8,792,719 | JPEG | no |
| wiki.gg, URL as returned | 8,740,911 | JPEG | no |

Two consequences, both binding on any future tier:

1. **`?format=original` is MANDATORY on Fandom.** Without it the default path is
   a lossy WEBP transcode. wiki.gg needs no such flag and is the cleaner default.
2. **The declared sha1 is NOT verifiable on the wire from either host.** Every
   path re-serves rather than streaming the stored blob, so provenance must
   record the sha256 of what was actually FETCHED, never assert identity to the
   API-declared sha1. Recording the declared sha1 as if it were the file's hash
   would be a manufactured green.

All variants decode at the full 7200x4400, so these are re-encodes, not resizes.

### Round 2B + 3 - corpus coverage

20 champions drawn from real slug names in `2.First Pass Done`. Round 2 used a
single `ailimit=500` call; round 3 re-ran three of them following `aicontinue`
to the end and proved 500 was the CAP, not the count:

| champion | round 2 (capped) | round 3 (full walk) |
|---|---|---|
| Vayne | 500 files, 12 HD | **1584 files, 19 HD** |
| Janna | 500 files, 15 HD | **543 files, 17 HD** |
| Nidalee | 500 files, 12 HD | **1201 files, 17 HD** |

**Every round-2 count is a lower bound.** Reported as such rather than restated
as a census: 19 of 20 champions carry `*Skin_HD.jpg` files, at least 147 HD files
across them, and **143 of 147 are at or above 2560x1440** - typically 5000x2950
to 10000x6105, with an 11084x6425 on Vayne. The four below target are the
1920x1078-to-2000x1125 legacy uploads.

The one apparent miss was NOT a miss. `Velkoz_` returned 2 files / 0 HD;
`Vel'Koz_` returns 534 files and 8 HD, all 8 at or over target (up to 8500x5089).
**A slug-to-title mapping is required and apostrophes are load-bearing** - the
same class covers `Kai'Sa`, `Cho'Gath`, `Kha'Zix`, `Rek'Sai`, plus the spaced
names (`Xin Zhao`, `Miss Fortune`, `Master Yi`, `Tahm Kench`, `Aurelion Sol`,
`Lee Sin`, `Jarvan IV`, `Dr. Mundo`, `Nunu & Willump`, `Renata Glasc`). Reading a
0 from a name guess as "the wiki does not have it" is the failure mode to avoid;
round 2 would have filed exactly that if round 3 had not been run.

## Verdict, and what is NOT claimed

**ADOPT the source, DECLINE both servers.** Prefer wiki.gg (byte-faithful
default, newer MediaWiki, no `format=original` dance); Fandom is the fallback and
MUST carry `?format=original` if used.

Deliberately NOT claimed, because it was not measured:

- **That this helps the existing corpus.** The wiki hosts OFFICIAL Riot splash
  art. A large part of LW's corpus is fan art off DeviantArt and wallpaper
  aggregators, which no wiki hosts. The recovery win is confined to slugs whose
  subject IS an official splash - unquantified here, and the honest next step is
  to count that intersection before building anything.
- **That a wiki HD file beats the file LW already holds** for any given slug. No
  per-slug comparison was run. A 7200x4400 canonical source would remove the AI
  upscale for those slugs entirely (ADR-002's one-upscale rule becomes a
  downscale-only passthrough, the same branch the 46 refs took), which is the
  prize - but it is a claim to measure, not to assume.
- **Licensing.** Wiki-hosted Riot art under LW's private-use boundary (ADR-005,
  RESTORATION_PLAN section 9) is unchanged by this probe and unexamined by it.

## Next, if funded

A Tier-0.5 canonical-source step ahead of Tier 1 in the recovery waterfall
(`docs/SOURCE_RECOVERY.md` ordering). Cheapest honest first slice, in order:

1. Count the intersection: how many corpus slugs name a champion AND a skin that
   resolves to a `*Skin_HD.jpg` title. Decides whether the tier is worth building
   at all.
2. Slug-to-title mapping with the apostrophe/space cases tested first, not last.
3. Fetch with the `format=original` rule and sha256-of-fetched provenance.
4. Compare pixels against the held `_firstinitial` per slug before promoting
   anything.

Do-not-redo, from this probe:

- Do NOT install either MediaWiki MCP server. The API is the capability; the
  servers are wrappers over it.
- Do NOT fetch a Fandom file URL without `?format=original` - the default is a
  lossy WEBP transcode that passes a dimensions check.
- Do NOT assert byte-identity to the API-declared sha1. No host serves bytes
  matching it.
- Do NOT read a per-champion `allimages` count without following `aicontinue`.
  500 is the cap and it silently truncates.
- Do NOT read a 0-result name guess as absence. Normalize the title first.
